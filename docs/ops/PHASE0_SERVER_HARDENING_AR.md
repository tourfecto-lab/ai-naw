# المرحلة 0 — إجراءات تُنفَّذ على السيرفر (خارج الكود)

هذه الخطوات تمس الموقع الحي، لذلك لم تُنفَّذ من الكود. نفّذها أنت أو من يدير الاستضافة، وخذ نسخة احتياطية من الإعداد قبل أي تعديل.

## 1) ملف الجلسة المرفوع إلى Git (الأهم)

كان الملف `public_html/storage/sessions/sess_56aftu8pj6jev0emkurcqijhte` مرفوعًا في المستودع. أُخرج من التتبع في هذا التعديل، لكنه ما زال في **تاريخ Git** (commit `6cf762c`) وعلى نسخة المستودع في GitHub.

**اعتبر ما فيه مسرّبًا** (وخصوصًا إن كان المستودع نُسخ أو شُورك يومًا) وافعل:

1. افتح الملف محليًا وحدّد `user_id` فقط.
2. من لوحة الأدمن أو قاعدة البيانات: غيّر كلمة مرور هذا المستخدم، وأعد توليد `api_token` / `api_key` الخاص به، وألغِ جلساته الفعّالة.
3. إن كان المستخدم أدمن، فعّل 2FA له إن لم يكن مفعّلًا.
4. بعد ذلك فقط يمكن تنظيف التاريخ (يتطلب `git filter-repo` ثم `force push`، ويعيد كتابة كل الـ commits، فلا يُنفَّذ إلا بموافقة صريحة منك).

## 2) تحويل HTTP إلى HTTPS (nginx)

الفحص أظهر أن `http://tourfecto.pro/` يرد 200 بدل التحويل. أضف server block منفصلًا للمنفذ 80:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name tourfecto.pro www.tourfecto.pro;
    return 301 https://tourfecto.pro$request_uri;
}
```

ثم `nginx -t` ثم `systemctl reload nginx`. (إن كان الموقع خلف Cloudflare فعّل "Always Use HTTPS" هناك بدلًا من ذلك.)

## 3) ترويسة HSTS المكرّرة

الاستجابة تحمل ترويستين: واحدة من PHP (`max-age=31536000; includeSubDomains`) وأخرى من nginx (`max-age=31536000`). أبقِ واحدة فقط. الأسهل: احذف `add_header Strict-Transport-Security ...` من إعداد nginx، فيبقى الكود هو المصدر الوحيد.

## 4) مفتاح التشفير

بعد هذا التعديل، `WhatsAppCloudController` و`MetaWebhookController` يتوقفان بخطأ بدل الاشتقاق من النص الثابت `'tourfecto'` إن غاب `ENCRYPTION_KEY` و`SALT` معًا. تأكد أن أحدهما معرَّف في `.env` على السيرفر **قبل** نشر هذا التعديل.

## 5) الويب-هوك القديم `/api/chat/webhook`

صار يرد `410` افتراضيًا. الاستخدامات الرسمية لا تتأثر (`/api/whatsapp-cloud/webhook` و`/api/meta/webhook` موقّعان). إن كان لديك تكامل مخصص يستخدمه فعلًا، أضف مؤقتًا في `.env`:

```
LEGACY_CHAT_WEBHOOK_ENABLED=1
```

وانقل التكامل إلى المسار الموقّع بأسرع وقت، فهذا المسار يثق في `user_id` القادم من الطلب.

## 6) CSRF

نمط الاستثناء أصبح مثبّتًا في بداية المسار. كان القديم يعفي أي مسار يحتوي `/webhook/`، ومنه `/api/site-connect/{id}/webhook` و`/api/email-marketing/smtp-settings/webhook` وهما لمستخدم مسجّل الدخول. **بعد النشر** جرّب من لوحة العميل: حفظ إعدادات SMTP webhook، وSite Connect، فإن ظهر خطأ 403 "الطلب ده مرفوض" فأخبرني بالمسار.

## 7) ما لم يتغير عمدًا

- **XPay:** الويب-هوك لا يرفض التوقيع غير المطابق. لم أغيّره لأن صيغة توقيع XPay تُجرَّب بأكثر من شكل في الكود، ورفض خاطئ قد يوقف شحن المحفظة. الحماية الحالية (إعادة جلب الجلسة من XPay والتحقق من المبلغ والعملة) كافية، فاعتبره منخفض الخطورة.
- **CSP:** تشديده (إزالة `unsafe-inline` و`unsafe-eval`) يحتاج إزالة الأنماط والسكربتات المضمّنة أولًا (المرحلة 3).

## التراجع

كل تعديلات الكود في commit واحد، ويمكن التراجع عنها بـ `git revert`.
